# 语义订阅

## 使用方式

新建订阅默认选择“语义订阅”。直接描述需要什么，并填写可选的排除条件，例如：

> 关注可在个人电脑上离线运行的开放权重语言模型，优先看安装教程、量化方法和性能实测；排除融资新闻、纯广告和只能调用云端接口的产品。

系统先调用已配置的模型理解需求，显示关注点与排除条件，再按理解后的主题选择候选来源。候选来源只是获取范围，来源中的每篇文章仍需单独审核。也可以手动添加来源，语义筛选仍然生效。

“试采预览”会显示推荐和未推荐的样本、评分与理由。语义试采会调用模型，但不创建订阅、任务、内容、通知或投递记录。内容中心可查看已经通过审核的文章、推荐理由及输入原文中的逐字依据，并可切换推荐优先或最新排序。

旧订阅保留原有关键词模式，需要编辑后明确切换。“关键词筛选（兼容）”是可选的独立模式，不是模型故障时的自动降级。额外翻译和简报与语义筛选分别设置；关闭翻译不会关闭语义审核。

## 判断过程

1. 模型将原始自然语言需求理解为关注点、排除条件、来源查询和目录分类。判断文章时仍提供原始需求，避免只依赖中间概括。
2. Scout 在语义模式跳过关键词包含过滤，按来源交替排列候选，避免首个来源耗尽评估额度。
3. Parser 清洗和尝试补全正文，先执行可读性检测，再调用模型逐篇判断语义相关性。
4. 判断包括相关度 0～100、是否符合需求、是否命中排除条件、中文理由和逐字原文依据。排除条件优先；推荐必须同时满足符合需求、未排除、达到阈值。
5. 只有审核通过的文章进入 Connector 去重、风险审批和发布。Curator 只为最终新增的已发布内容生成通知/推送。

标准阈值为 75，可选择 60 或 85。每次正式采集默认最多评估 20 条候选，可选 10/40；试采最多评估前 10 条。每批最多 5 条，最多两个语义评估批次同时运行。超出预算的内容明确记为未评估，不会自动当作已拒绝或已推荐。原始采集每源最多 50 条、Scout 最多交给解析器 100 条的限制仍然存在。

正文片段提供标题前 300 字、源摘要前 600 字和清洗正文前 1800 字，因此模型不能保证理解超出片段的信息。缺少用户硬性条件的证据时要求不推荐；评分表示相关程度，不是事实准确率或成功概率。试采与正式采集使用同一筛选实现，但抽样数量、正文补全数量和来源内容更新时间不同，结果不保证逐条相同。

## 失败保护与成本控制

- 模型未配置、超时、返回非法 JSON、遗漏/重复文章 ID、字段类型错误、评分越界、匹配时缺少引文，或引文不存在于对应输入中，均停止本批处理。正式任务失败，不发布未经审核的内容。
- 文章作为不可信数据传入模型，系统提示禁止执行其中改变评分或格式的指令；模型没有工具调用权限。严格格式和引文检查可以发现一部分错误，不代表能够消除所有模型误判或指令干扰。
- 单个批次失败会取消同轮其他未结束的模型请求。结构化语义调用关闭 SDK 自动重试，避免超时后无提示地重复推理；用户可在任务中心重试。
- 需求理解缓存最多 128 条，文章判断缓存最多 1000 条，均为进程内 24 小时缓存。缓存键包含需求、排除条件、阈值/预算、模型标识及文章片段等信息；改变条件不会误用旧判断。重启会清空缓存。
- 语义模型请求读取超时为 75 秒，理解/评估单次外层时限为 90 秒。语义任务执行上限 600 秒，兼容模式任务仍为 300 秒；语义试采阶段上限 240 秒，需求理解在此之前执行。服务繁忙时可能因排队或总时限失败。
- 当前尚无按用户计费或日用量配额，模型用量取决于评估预算、订阅频率和缓存命中。应先用小预算试采，再按需要增大。

当前配置为 DeepSeek 官方端点时，语义调用使用 JSON 输出并关闭默认思考模式，以控制结构化判断的延迟；依据其[思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)和[JSON 输出说明](https://api-docs.deepseek.com/guides/json_mode/)。其他兼容端点通过提示约束 JSON 并执行相同的本地校验，不发送 DeepSeek 专用参数。

## 数据与接口

策略保存在 `trigger_conditions.semantic_filter`：

```json
{"enabled":true,"intent":"想关注的内容","exclusions":"排除条件","threshold":75,"max_candidates":20}
```

`content.relevance` 保存通过审核文章的评分、理由、引文、需求快照、模型标识和判断时间。任务状态保留理解结果、评估/推荐/拒绝/未评估数量及拒绝理由。未推荐文章不会作为可读内容入库。旧文章显示未经过语义筛选，不猜测回填分数。

- `GET /api/python/subscriptions/semantic-capabilities`：是否已配置模型及预算默认值，不返回密钥。
- `POST /api/python/subscriptions/interpret`：理解语义需求。
- `POST /api/python/subscriptions/resolve-sources`：可附 `semantic_policy`，按理解结果选源。
- `POST /api/python/subscriptions/trial`：可附 `semantic_policy`，语义试采。
- `GET /api/python/contents?sort=relevance`：优先近期采集日，再按相关度排序；采集日期以数据库 UTC 日期分组。`sort=latest` 按采集时间排序。

来源自动匹配、手动添加、Java 写入入口和 Python 定时/手动任务都支持相同语义策略。来源自动匹配时可能对少量未检测来源执行健康检查；试采本身不会写入健康记录。

## 验证

`nexus-python/tests/fixtures/semantic_cases.json` 为 8 条明确标注的合成验收文章。真实配置模型本轮结果为 **8/8 符合预期**：中文同义表达和英文实操文章推荐，其余融资、云服务、纯发布、信息不足、干扰指令及超出硬件条件的内容不推荐。该结果只覆盖这组小样本，不代表所有真实文章的准确率。

```powershell
# 会调用当前配置的真实模型；不发布文章：
python scripts/semantic_eval.py --real-model

# 完整服务联调使用明确标注的本地模拟模型，验证协议与业务行为；
# 会暂时重启应用，结束时恢复真实配置，且不向真实群推送：
python scripts/semantic_stack_check.py
```

结果分别保存在 `.runtime/semantic-eval-result.json`、`.runtime/semantic-stack-result.json`，浏览器截图 `.runtime/semantic-trial.png`。完整联调确认 8 条候选只发布 2 条、6 条拒绝；坏 JSON 导致任务失败且没有新增内容/通知；试采不写入业务记录；推荐理由持久化、排序与 390px 界面通过。
